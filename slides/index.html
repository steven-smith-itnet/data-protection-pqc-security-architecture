Executive briefing

Data protection and post-quantum encryption

A phased program for a global hospitality organization: inventory, classification, encryption, key management, and the move to post-quantum cryptography across on-prem, AWS, Azure, Google Cloud, and OCI.

Steven W. Smith · reference architecture

Key objectives

  • Know where sensitive data is, structured and unstructured, on-prem and in every cloud
  • Classify and label it so the correct control is applied automatically
  • One cryptographic standard and one key management model with separation of duties
  • Reduce PCI DSS scope with P2PE and tokenization
  • Meet privacy and residency obligations (GDPR, CCPA/CPRA, PIPL, LGPD, DPDP)
  • Protect data in transit and, where it matters, in use
  • Be ready for post-quantum cryptography, with crypto agility built in
  • Give engineering teams paved roads, patterns, and fast design reviews

Why encryption alone is not enough

Found and labeledA control cannot be applied to data nobody knows exists. Discovery and labeling come first.
Keys managed properlyIf the same people and roles hold the data and the keys, encryption limits nothing.
Algorithms that lastData kept for ten years needs protection that is still strong in ten years.

Transparent disk and database encryption protect against stolen media. They do not protect against a compromised application, an over-privileged administrator, or SQL injection.

Good, Better, Best

Good: PP-1 BaselineProvider-managed keys, default encryption at rest, TLS 1.2 or later, standard IAM, audit logging.

Public, Internal
Better: PP-2 EnhancedCustomer-managed keys per data domain, rotation, key admin and key user separation, TDE with CMK, dynamic masking, DLP, hybrid PQ TLS where offered.

Confidential
Best: PP-3 MaximumField-level encryption or tokenization in the application, single-tenant HSM or external keys where justified, persistent file encryption, mTLS, confidential computing, crypto-shredding.

Restricted

Best is not always right: external keys add outage risk, and field-level encryption breaks search and joins. Each choice is justified by the data tier.

Unstructured data: protection that travels

Storage-boundS3, Blob, GCS, OCI Object Storage, NAS encryption with CMK. Protection ends when the file is downloaded.
PersistentPurview sensitivity labels with encryption, rights management, DKE for the most sensitive. Protection stays with the file.
EnforcedAuto-labeling, DLP keyed on labels and sensitive information types, CASB for SaaS, bucket policies that reject the wrong key.

Hospitality targets: front-desk ID scans, rooming lists in Excel, PMS exports, event contracts, CCTV, call recordings.

Envelope encryption everywhere: a data key per object or record, wrapped by a key-encryption key that never leaves the HSM boundary. Re-wrapping keys is cheap; re-encrypting data is not.

Transit and in use

  • TLS 1.3 by default, TLS 1.2 allowed with an approved cipher list, nothing older
  • mTLS between services through a service mesh; SPIFFE workload identities
  • Database connections require verified TLS; property-to-cloud links encrypted end to end
  • Public certificate lifetime falls to 200 days (March 2026), 100 days (2027), 47 days (2029): certificate automation is mandatory
  • Confidential computing (Nitro Enclaves, SEV-SNP, TDX) for payment and partner analytics workloads that justify it

Why post-quantum now

Harvest now, decrypt laterTraffic recorded today can be decrypted once a cryptographically relevant quantum computer exists.
Mosca's inequalityIf data shelf life plus migration time exceeds time to a quantum computer, the migration is already late.
Long-lived hardwareDoor locks, terminals, and HSMs installed now may still run in 2035.

Shor's algorithm breaks RSA, DH, ECDH, and ECDSA. AES-256 and SHA-384 remain appropriate.

PQC migration sequence

1. InventoryCBOM of algorithms, certificates, keys, libraries, HSMs
→
2. PrioritizeShelf life, exposure, replacement difficulty
→
3. Hybrid key exchangeX25519MLKEM768 at edges, gateways, mesh
→
4. Signatures and PKIML-DSA, SLH-DSA, LMS for firmware and roots
→
5. CompleteRemaining RSA/ECC retired by 2035

Crypto agility is the design principle: algorithm identifiers stored with ciphertext, central TLS termination, short-lived certificates, and a crypto provider abstraction in code.

Proof: hybrid PQ TLS on OpenSSL 3.5


# Server offers only the hybrid group
openssl s_server -accept 8443 -cert cert.pem -key key.pem \
  -tls1_3 -groups X25519MLKEM768 -www

# Client requests it and reports the negotiated group
openssl s_client -connect localhost:8443 -tls1_3 \
  -groups X25519MLKEM768 -brief </dev/null

The full lab runs ML-KEM encapsulation, ML-DSA and SLH-DSA signatures, an ML-DSA certificate, and the hybrid handshake, with captured output. See Hands-on PQC lab.

Enabling engineering teams

  • Intake by classification: C0 and C1 self-serve; C2 lightweight review; C3 full review with threat model
  • Paved roads: Terraform modules that pick the key from tags; approved crypto libraries per language
  • Decision trees: which layer, which key custody, tokenize vs encrypt vs mask
  • Guardrails: SCPs, Azure Policy, org policies, and OPA checks on Terraform plans
  • Encryption design record: a one-page ADR for every C3 system
  • Champions and office hours so review is not a bottleneck
